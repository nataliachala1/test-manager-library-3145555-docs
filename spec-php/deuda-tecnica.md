# Deuda técnica registrada — Manager Library (PHP/Laravel)

Este registro no amplía el producto ni modifica su alcance. Contiene decisiones de implementación que pueden resolverse después de
cerrar la documentación funcional y contractual.

| ID | Deuda | Impacto | Prioridad | Criterio para cerrarla | Estado |
|---|---|---|---|---|---|
| DT-001 | Elegir y documentar el paquete Laravel para emitir y validar JWT HS256. | Seguridad y mantenimiento. | Media | El paquete cumple el contrato, expone `sub` y `role`, y tiene pruebas de expiración y firma. | Pendiente |
| DT-002 | Definir la implementación de producción para `CoverStorage` (disco local o S3). | Operación y respaldo de portadas. | Media | Existe un adaptador probado; el contrato HTTP permanece igual. | Pendiente |
| DT-003 | Definir la herramienta concreta para validar las reglas de arquitectura PHP. | Automatización de calidad. | Media | Las reglas de los artículos I, II y III fallan ante una dependencia prohibida. | Pendiente |
| DT-004 | Fijar el procedimiento final de disponibilidad de PostgreSQL en Docker Compose. | Arranque local y reproducibilidad. | Media | `docker compose up` espera salud de la base, ejecuta migraciones y deja disponible la API. | Pendiente |
| DT-005 | Definir el entorno exacto de la medición de 300 ms con 5 000 libros. | Comparabilidad del requisito RNF-1. | Media | Se documentan hardware, carga, consulta y umbral de aceptación. | Pendiente |
| DT-006 | La FK `loan_item.loan_id` usa `ON DELETE CASCADE`, capaz de borrar líneas históricas si se elimina un préstamo directamente, mientras la retención indica que préstamos y líneas no se borran. | Pérdida irreversible de historial; impide garantizar CA-06.7 y la retención documentada ante borrado accidental/directo. | Alta | El propietario de arquitectura decide y documenta una protección compatible con la retención (p. ej., FK restrictiva o mecanismo equivalente); `data-model.md`, migración y verificación quedan alineados. | Bloqueante |
| DT-007 | Las convenciones de Eloquent no coinciden automáticamente con esquema `library`, tablas singulares, UUID, ausencia de timestamps y baja lógica solo en `book`. | Persistencia puede consultar o modificar tablas/columnas equivocadas, o borrar datos fuera de las reglas. | Alta | Configuración y mapeos explícitos documentados; integración verifica nombres, claves, esquema, timestamps y `deleted_at` contra `data-model.md`. | Pendiente |
| DT-008 | El contrato público de `POST /loans` no permite fijar `loaned_at`; con vencimiento a 14 días el sembrador por API no puede crear datos vencidos reproducibles para la demostración actual. | T-21 no puede acreditar sus tres vencidos sin esperar 14 días o cambiar reglas/contrato. | Alta | Se aprueba un procedimiento de fixture/reloj de prueba que no añade endpoints ni cambia reglas de negocio, y se documenta evidencia reproducible; no está decidido. | Bloqueante para T-21 |
| DT-009 | El contrato define un cuerpo de error único y estados, pero queda por concretar su traducción desde validación/excepciones de Laravel y la respuesta de errores de transporte (incluida autenticación y multipart de portadas). | Respuestas inconsistentes y pruebas de contrato incompletas. | Alta | El adaptador HTTP mapea todos los errores definidos al cuerpo y códigos documentados; pruebas de contrato comprueban 401, 403, 404, 409 y 422 sin filtrar detalles internos. | Pendiente |
| DT-010 | El README raíz todavía afirma que el repositorio contiene solo `spec-python/` y `spec-.net/`, mientras existe esta especificación `spec-php/`; corregirlo queda fuera de la autorización limitada a esa carpeta. | Lectores pueden elegir una especificación o stack incorrecto. | Media | El README raíz se actualiza por una tarea autorizada fuera del alcance actual y enlaza la versión PHP/Laravel. | Pendiente externo |
| DT-011 | `book.version` no serializa préstamos simultáneos de distintos libros del mismo socio; el conteo máximo de tres líneas abiertas puede excederse en una carrera (CA-06.4). | Invariante funcional concurrente no garantizada; HU-06 no se puede implementar completamente con la decisión actual. | Alta | Se aprueba y documenta una estrategia transaccional para serializar/revalidar por socio; ADR-002, API y tareas especifican la respuesta al conflicto y una prueba concurrente demuestra el límite. | Bloqueante |
| DT-012 | El contrato asigna 401 a token ausente, inválido o vencido, pero la tabla de códigos solo define INVALID_CREDENTIALS para 401; el cuerpo único requiere un código. | No se puede completar el contrato de error ni la evidencia HTTP de HU-01 sin introducir una decisión de código. | Alta | El propietario aprueba/documenta el código para fallos de autenticación distintos de credenciales inválidas y se alinea la tabla de códigos con CA-01.3; no se inventa aquí. | Bloqueante para cierre del contrato |

## Reglas del registro

- Ninguna deuda autoriza agregar funcionalidades fuera de `spec.md`.
- Ninguna deuda bloquea el cierre del contrato HTTP o del modelo de datos.
- Cada deuda debe conservar el alcance actual y tener un criterio verificable de cierre.
